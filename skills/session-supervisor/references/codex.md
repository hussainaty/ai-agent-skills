# Codex session adapter

`codex_adapter.py` provides project-scoped, read-only wrappers around the existing Codex app-server helpers. `CodexAdapter(directory, command=None, timeout=30)` exposes `list_sessions(limit=10)`, `session_status(session_id)`, `session_outcome(session_id, authorized=True, max_chars=4000)`, `goal_status(session_id)` and `rate_limits()`. The helpers must be on the Python module search path; package them in the same script directory. Outcome reads require caller-confirmed, specific session authorization; a boolean is not an access-control system. Native Codex app tools should be preferred when the host exposes them. When the API exposes only a subset or an error, report the limitation rather than inventing state.

`wake_decision(...)` is a pure assessment, not a scheduler or sender. It requests explicit per-session authorization and evidence that a failure was a temporary limit, that the prior limited turn is terminal, that any previous delivery of this new wake is confirmed not accepted or not sent, and that a valid reset has been reached. The terminal turn can have made changes: continuation must inspect existing work and must not replay the original prompt. After reset it also checks a fresh account-limit reading, a host-confirmed desktop-wide idle state, a resumable Goal, absence of pending approval/user input, and an atomic host dispatch capability. Unknown is not success. Even the most favorable result is `host_handoff_only`; it does not send or authorize a prompt, and the real host must atomically recheck and deduplicate. A caller-supplied flag is not proof of authorization or of the host capability.

The installed Codex CLI documents `codex exec resume SESSION_ID - --json`, where `-` can read a follow-up prompt from stdin and JSONL exposes events. The installed app-server schema includes typed `rateLimitExceeded` and `usageLimitExceeded`, and account windows include `resetsAt`. A 429 alone does not prove the task had no earlier side effects or that a billing/quota problem is transient. An independent reader's `idle`/`notLoaded` status is not proof that the desktop UI is globally idle. `turn/start` can steer an active turn and has no documented idle-only compare-and-set precondition. A model instruction to ignore messages cannot replace host-level concurrency control.

A separate managed worker can use cooperative single-owner conventions, but this cannot stop a user or the desktop from opening or steering the same session. An unknown continuation delivery must not be retried blindly. Partial work from a confirmed terminal turn is preserved and inspected by the new continuation, not replayed as if unapplied. No atomic host dispatch or autonomous rate-limit wakeup was demonstrated on this machine. The only live check here was a read-only status and Goal query against the current chat, without inference; the fake app-server tests verify project boundaries, metadata redaction, and conservative decisions.
